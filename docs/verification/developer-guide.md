# Developer guide: adding a new fuzzer lowering

This guide is for maintainers changing the verification pipeline.

Related documents:

- [User guide](./README.md)
- [Schema migration guide](./schema-migration.md)
- [Golden fixtures](./fixtures/README.md)

## 1. Where changes usually belong

The lowering pipeline is split across a few files.

- `crates/aiken-lang/src/test_framework.rs`
  - typed/source-level fuzzer normalization
  - helper-function resolution
  - combinator decomposition (`map`, `mapN`, `and_then`, `such_that`, lists, sets, tuples, options, choices, scenarios)
- `crates/aiken-project/src/export.rs`
  - exported JSON shape for normalized fuzzer structure, mapper shapes, source spans, schemas, and test metadata
- `crates/aiken-project/src/lib.rs`
  - conversion from language-level normalized fuzzers into exported structures
- `crates/aiken-project/src/verify.rs`
  - `DomainRel` lowering
  - precision/certificate/obligation assignment
  - trust-profile compatibility checks
  - theorem generation and result classification
- `crates/aiken-project/src/verify/tests.rs`
  - lowering, theorem-shape, sampler, scenario, bridge, and compatibility regressions
- `crates/aiken/src/cmd/verify.rs`
  - CLI output, JSON contract snapshots, and user-facing fixture coverage

Do not add a new ad hoc lowering in only one layer. The exported structure, result metadata, and theorem shape must stay coherent.

## 2. The non-negotiable rule

A lowering is finished only when the system can tell the truth about the relation between the theorem domain and the real fuzzer.

That means every new lowering must answer:

1. What values can the real fuzzer generate?
2. Does the exported `DomainRel` describe exactly those values, a superset, a subset, or only replayed witnesses?
3. Why should anyone trust that claim?
4. Which obligations remain open if the answer is not complete?

If you cannot answer all four, the lowering is not `Exact`.

## 3. Choosing `DomainPrecision`

### `Exact`

Use `Exact` only when all of the following are true:

- the generated relation matches the fuzzer support, not just a convenient predicate
- no schema-less raw-`Data` fallback is involved
- no placeholder, `sorry`, `admit`, skipped branch, or local `True` widening remains
- the theorem mode actually allows exactness to matter in the reported direction
- the certificate is strong enough for the trust profile

Typical acceptable `Exact` sources:

- a Lean-proved relation (`LeanProved`)
- a pinned/hash-checked trusted model (`TrustedVersionedModel`)
- an exact sampler semantics statement (`SamplerSemanticModel`)

Do **not** mark replay-only evidence as `Exact`. Concrete replay belongs in `WitnessOnly` or sometimes `UnderApprox`, not `Exact`.

### `OverApprox`

Use `OverApprox` when the domain safely contains every generated input, but may include additional values.

Use this for:

- universal `normal` theorems
- universal `fail` theorems
- schema fallback that keeps sound coverage but loses exactness
- `such_that` without exact retry semantics
- bytearray/content abstractions that preserve length but not full content semantics

Do **not** use `OverApprox` alone as existential evidence for `fail_once`.

### `UnderApprox`

Use `UnderApprox` when every domain value is generated by the real fuzzer, but the domain does not claim full coverage.

Use this for:

- replay-backed or finite witness domains used for semantic `fail_once`
- conservative finite search domains that are known generated inputs but not the full support

Do **not** use `UnderApprox` for universal success/failure claims.

### `WitnessOnly`

Use `WitnessOnly` for concrete replayed/generated values only.

Use this when the system can validate a specific witness/trace but cannot honestly claim a broader semantic domain.

### `Unknown`

Use `Unknown` when the relation is not justified.

Common causes:

- opaque child term with no usable sampler theorem
- missing decoder/schema support
- placeholder or compatibility downgrade
- theorem/domain mismatch that the compatibility validator refuses

`Unknown` must not produce production-success.

## 4. Choosing `DomainCertificate`

### `LeanProved`

Use when Lean itself discharges the domain relation, not just the property theorem.

### `TrustedVersionedModel`

Use only when:

- the lowering comes from the pinned trusted model
- the relevant model/hash fields are present and checked
- regression tests pin the expected model/package hash where appropriate

If the hash changed unexpectedly and you have not re-established the model, this certificate is wrong.

### `SamplerSemanticModel`

Use when the relation is expressed directly over the stable sampler harness ABI / UPLC semantics, not over an informal summary.

### `WitnessReplay`

Use for concrete replay-backed evidence.

This is appropriate for `WitnessOnly` and some `UnderApprox` existential paths.

### `DifferentialTestedOnly`

Use only for regression evidence. This is not production proof by itself.

`production` must reject it. `experimental` may accept it with visible warnings.

### `Unchecked`

Use for placeholders, unproven bridges, unresolved compatibility gaps, or anything else that lacks proof-grade justification.

`Unchecked` must not yield production-success.

## 5. Obligations are part of the API

Whenever you add a lowering, decide which obligations are discharged and which stay open.

Typical obligations:

- `FuzzerReturnsImpliesDomain`
- `DomainImpliesFuzzerReturns`
- `DomainIffFuzzerReturns`
- `WitnessReplaysThroughFuzzer`
- `WitnessSatisfiesDomain`
- `FuzzerModelHashMatches`
- `ValueDecoderRoundTrip`
- `FuzzerOutputTypeMatchesPropertyInputType`
- `PropertyHarnessAcceptsDecodedInput`
- `PropertyHarnessMatchesExportedUPLC`

Do not silently omit a missing proof obligation. If it matters to correctness, it must appear as open.

## 6. Local fallback rules

Prefer preserving known structure with a local fallback over collapsing the whole fuzzer to unsupported.

Examples:

- known `mapN` with one opaque child: keep the `Image` / `Product` structure and lower the opaque child to `SamplerReturns`
- supported tuple fields plus one unresolved branch: keep the tuple relation and attach diagnostics/widenings to the unresolved part

But be conservative after doing so:

- precision usually becomes `Unknown` or `OverApprox`
- compatibility checks may need to downgrade success to `Partial`
- source-span diagnostics should point at the widened/opaque construct

## 7. Required tests for every new lowering

A new lowering is not complete without targeted tests.

### In `crates/aiken-lang/src/test_framework.rs`

Add normalization/source-level tests showing the extractor recognizes the new combinator or helper shape.

Use the existing style around tests such as:

- `normalize_fuzzer_...`
- `tuple_elem_arg_index_prefers_mapper_binder_over_outer_local_alias`

### In `crates/aiken-project/src/verify/tests.rs`

Add result-shape and safety tests covering at least:

- the new `DomainRel` JSON shape
- precision/certificate assignment
- open vs discharged obligations
- compatibility behavior for `normal`, `fail`, `fail_once`, and witness modes as applicable
- sampler fallback or scenario metadata when relevant

Useful test families already exist under prefixes such as:

- `primitive_...`
- `composed_...`
- `sampler_...`
- `fail_once_...`
- `scenario_...`
- `compatibility_...`
- `counterexample_...`
- `parse_verify_results...`
- `status...`

### In `crates/aiken/src/cmd/verify.rs`

If the user-visible JSON or text contract changes, update:

- JSON contract snapshots
- docs fixtures under `docs/verification/fixtures`
- any text output snapshots or capability/doctor contract tests

## 8. Exactness checklist before you merge

Before choosing `Exact`, ask all of these:

- Is the relation actually equal to the generator support?
- Are retry/failure semantics modeled, not hand-waved?
- Are decoding and harness obligations discharged?
- Is the certificate strong enough for `production`?
- Would a `fail_once` theorem still be sound if the domain were reused there?
- If the model/package hash changed, would this test fail loudly?

If any answer is “no”, do not mark it `Exact`.

## 9. Commands maintainers should run

At minimum, after changing a lowering:

```text
cargo +1.94.1 test -p aiken-lang normalize_fuzzer_
cargo +1.94.1 test -p aiken-project <focused-prefix>
cargo +1.94.1 test -p aiken cmd::verify::tests::
cargo +1.94.1 run -p aiken -- verify run examples/acceptance_tests/property_smoke --artifacts always --timeout 2400 --json
```

Replace `<focused-prefix>` with the narrowest family that covers the change (`primitive_`, `composed_`, `fail_once_`, `sampler_`, `scenario_`, `counterexample_`, and so on).

If you changed a schema, status, or fixture surface, run the fixture/doc tests too.

## 10. What not to do

Do not:

- mark `OverApprox` as existential evidence for `fail_once`
- mark replay-only evidence as `Exact`
- keep missing decoder/schema support implicit
- treat `DifferentialTestedOnly` as production proof
- emit `SolverValidated` or `LeanCertified` from `Unknown` / `Unchecked` domains
- collapse a local unsupported child into a fake global success theorem
- update the theorem template without updating manifest metadata and docs
