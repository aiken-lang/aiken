## 2026-11-04 — UAL-02: standalone document contracts

- Added `aiken-ual` through the workspace's existing `crates/*` membership. It has no dependency on `aiken-lang`, `aiken-project`, `uplc`, Lean or Z3. The existing `cryptoxide` dependency supplies SHA-256; `jsonschema` 0.33 supplies draft-2020-12 validation with default HTTP/file retrieval features disabled and an explicit rejecting retriever, including under Cargo feature unification.
- Followed [PlutusCoreBlaster `1c23de8f35fdc5decf6f126c7b56ed6649e4a57f`](https://github.com/input-output-hk/PlutusCoreBlaster/tree/1c23de8f35fdc5decf6f126c7b56ed6649e4a57f/PlutusCore/UPLC/BlueprintEncoding), not moving upstream. No old integration branch code was used.
- The ticket calls the document contract UAL 0.6. Per plan §4.1, the pinned coordinated workspace identifies UAL 1.0 (`1f7ab84`); the plan records this as the 0.6-draft rename without a content change. Wire schema identifiers remain the pinned `cipXXXX` / compiled-interface-v1 identifiers. The model does not invent a top-level UAL version field: assurance preamble and language registries retain their explicit versions. Temporal operators and Lean elaboration remain out of scope.
- Canonical file encoding is recursively lexicographically sorted JSON object keys, serde_json's two-space pretty formatting (including multiline nonempty arrays), UTF-8 strings and one trailing LF. Array order is preserved. Explicit recursive sorting makes bytes independent of `serde_json/preserve_order`. This is a fixed producer encoding, not RFC 8785. Hash existing files as raw bytes; parsing and normalizing them before hashing would invalidate bindings. Independent golden fixtures cover each document, including evidence-bearing assurance.
- The schema's semantics variants are uppercase `A`–`E`; Aiken's future lowercase `c`/`e` syntax must lower to `C`/`E`. Universal validator checking targets contain validator id, purpose and parameter mode, not a template script-hash field. Their template hashes live in the digest-bound blueprint; applied targets additionally carry `appliedScriptHash`. Function targets carry SHA-256 plus a complete interface copy. The crate follows these pinned shapes, including schema-valid ledger-unit/applied forms, without claiming the pinned consumer executes every schema-valid form.
- The base blueprint schema contains legacy argument/parameter references whose files do not ship in the pinned set. The compiled-interface dialect reaches only its exact `$defs/preamble`. Unlike the consumer's on-demand resolver, the Rust validator eagerly crawls resources; the offline registry therefore exposes that unchanged preamble subtree under the base `$id` and rejects validation through the base root. Vendored bytes are untouched. Missing legacy refs are not downloaded or replaced by permissive schemas. Tests exercise preamble constraints and rejection of the base root.
- No environment schema ships at this pin. `schemas/environment.schema.json` is explicitly local and derived from `Assurance.lean::captureCheckingEnvironment`: format `blaster-loaded-environment-v1`, compiler/solver/module SHA-256s, optional native library SHA-256, and fixed solver options `60/100000/0`. There is no `$schema` in the manifest. Shape/hash validation is not equality with a live loaded environment; the consumer owns that check.
- Models preserve absent versus present-empty optional collections and retain unknown fields where upstream objects are open. Closed objects reject unknown fields; empty tagged struct variants are used because serde unit variants otherwise silently discard extra members. `ValueSchema` retains extensible schema JSON without inventing a second type/encoding system. Structural validation does not resolve value-definition graphs or analyze formal source.
- `function_digest` hashes hex-decoded `compiledCode`, including its single CBOR wrapper, with bounded decoding scratch space. Script hashes are carried as lowercase blake2b-224 hex and shape-checked, not recomputed by this crate. `validate_bindings` checks exact blueprint/context bytes, function code/interface identity, target coverage and evidence bindings; `validate_environment` separately checks manifest bytes. Callers supply artifact bytes and resolve paths; no implicit filesystem/network access occurs. Validator references resolve by id, then unique title, matching the pinned consumer.
- Evidence-bearing `verified-assurance.json` uses the same assurance document model. `EvidenceRecord::smt_check` binds a caller-reported outcome to a context digest, tool and artifact; callers add the scoped script/function hashes before validation. Construction does not invoke a solver or establish trust. Producer generation remains evidence-free; UAL-12 can use this write API after checking. Historical evidence is readable, but explicit binding validation rejects stale context/function/script hashes rather than treating it as current verification. The pinned schema's single `scriptHash` per evidence record remains unchanged.

A fresh-target offline build also passed with Lean/Lake/Z3 absent from PATH. No existing snapshots were changed.

## 2026-11-04 — UAL-05: Lean-free annotation model

- `aiken check` and `aiken build` run this front half after the complete project's type checking and before tests or blueprint generation, through the shared `Project::compile` path. Annotation errors use ordinary project diagnostics. `Project::annotation_model()` exposes the same validation on demand without a second cached model. No Lean process, target compilation, purpose lowering, assurance file emission, or evidence generation is part of this pass.
- Followed the ticket's Aiken header grammar and plan §2.1: `PREDICATE <Lean text>` and `PROPERTY <id> for <scope>+ "<description>" <Lean proposition>`. The [pinned UAL specification at `1f7ab84`](https://github.com/input-output-hk/UniversalAnnotationLanguage/blob/1f7ab84/UniversalAnnotationLanguage.md) illustrates Plinth's `[scope: ...]` header and colon before the proposition; those are not alternate Aiken headers. Unknown headers are errors, and an `ONCHAIN` block directs the user to `@onchain`. Descriptions support escaped quotes, backslashes, and `\n`, `\r`, `\t`; empty/whitespace-only descriptions and empty bodies are rejected. Bodies retain their original whitespace and UTF-8 bytes.
- `assurance::emitted_target_id` owns ADR-0007's mapping. Functions and validators share one target registry, so same-kind and cross-kind id collisions report both original qualified targets. Scopes resolve only against declarations in the property's checked module, not imported names. Validator selectors accept defined handlers and `else`, including implicit fallback; function selectors reject suffixes. Missing decorators provide a labelled scope, help text, and an insertion template requiring the author to choose steps and semantics rather than inventing an execution budget.
- One fragment per predicate-bearing module retains predicate blocks in source order. Imports follow source-ordered `use` edges, stopping at the nearest fragments and traversing through modules without predicates. Duplicate paths through a diamond are deduplicated. Properties without local predicates inherit imported fragment roots. Helper collisions are checked in each property's transitive closure, not across unrelated fragments.
- Fragment namespaces preserve checked module-path segments and escape invalid Lean identifiers and core keywords with `«…»`. Existing upstream behavior: `Project::module_name` already normalizes filesystem hyphens to underscores before type checking. This pass does not change Aiken module identity or perform another normalization; the namespace helper also handles verbatim hyphenated segments supplied in checked modules. Lexical character/keyword rules follow [Lean 4.24.0](https://github.com/leanprover/lean4/tree/v4.24.0/src/Lean/Parser), matching plan §4.1; no pins moved.
- Helper discovery is lexical, limited to visible `def`/`abbrev` names. It ignores nested Lean comments, strings, raw strings, character literals, and quoted names; redundant identifier escapes normalize without conflating an escaped dot with qualification. Fragment namespaces do not silently isolate duplicate helpers: the pinned consumer elaborates a property's closure together. Lean elaboration, imported syntax extensions, macro expansion, and the consumer's restricted expression profile remain consumer checks, not claims made by this model.
- Existing parsing and inference already accept annotation-only and import-only modules and retain typed `use` edges, so no language/compiler AST change was needed. An unused module-import warning is suppressed only when a parsed Lean body lexically references that import's alias or full namespace. Descriptions, comments, strings, and longer identifier prefixes do not count; unrelated warnings and modules without annotations retain their existing behavior.
- Diagnostics retain source byte spans and named source files; duplicate properties, target collisions, and helper collisions include related declaration locations. Added 29 focused tests covering header diagnostics, scope restrictions, both target-collision kinds, project-wide property uniqueness, fragment diamonds, helper visibility, annotation-only compilation, and warning behavior. One new reviewed JSON snapshot records the multi-module model, including normalized settings, escaped namespaces, ordered predicate blocks, and mixed function/validator handler scopes; no existing snapshots were changed.
- CLI smoke passed `check --deny` and `build --deny` for an annotation-only predicate module and an annotated validator with `.mint`/`.else` scopes, and executed an ordinary Aiken test. Both commands rejected ONCHAIN blocks, missing decorators, unknown scopes, and function suffixes with labelled source diagnostics; failed commands left the existing blueprint unchanged. A helper-collision smoke reported the property and both defining source files. No protected generator/evaluator paths, dependencies, or release/CI configuration were changed.
- Final verification passed: `cargo build --workspace --all-targets`, `cargo build --workspace`, `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test --workspace`, and bounded `aiken-acceptance`. Fragments preserve predicate text and imports, properties retain `formal.uses`, and every document uses the existing pinned schemas. Assurance language metadata records Lean 4.24.0 and UAL 1.0 with the full UAL commit read from the vendored workspace lock.

## 2026-11-04 — UAL-08: generate command and write-free dry runs

- Added `aiken verify generate [DIRECTORY] --environment PATH`, with the same trace parsers and silent default as build, plus `--env` for Aiken configuration selection. The manifest path is relative to the invocation directory; emitted environment references are relative to each project's `assurance/` directory. Workspace members use the existing workspace expansion. No consumer, Lean elaboration, solver or evidence generation is invoked.
- Per plan §4 and ADR-0001, `--no-environment` is the unbound dry run and conflicts with `--environment`. It compiles, validates annotations, generates target code, lowers properties and validates the draft schemas/definition graphs, but does not fabricate an environment or serialize an unrunnable bundle. Also exposed `--dry-run` with `--environment` to exercise manifest validation, context serialization and the complete byte-binding validation without writing. Diagnostics and exit status remain active in both modes; success explicitly reports the unbound environment when applicable.
- Existing `Project::compile`, even with `CodeGenMode::NoOp`, creates dependency directories, locks and package metadata. Added `compile_read_only` sharing the ordinary compilation/typechecking path while reading only an existing dependency installation. Dependency-free projects need no build directory or lockfile. Missing/stale dependency inputs fail with an instruction to run `aiken build`; dry runs never download, acquire filesystem locks, refresh caches, prune packages or create temporary files. Ordinary build/docs dependency behavior is unchanged.
- Read and validate environment manifests through `aiken-ual`, hash their original bytes, bind every checking context, and write the bundle API's immutable canonical bytes unchanged. Manifest shape/hash checks do not establish equality with a live loaded consumer. Pins from plan §4.1 and the vendored schemas remain unchanged; no moving upstream inputs or rejected integration-branch code were used.
- The pinned assurance schema requires authors and a creation date, but project configuration has no dedicated assurance metadata. Use the declared package owner as author and the UTC modification date of `aiken.toml` as creation date; title/version/description/license come from project configuration. This avoids wall-clock invocation timestamps and preserves rerun bytes for unchanged project metadata. Changing the manifest's modification date can change the assurance preamble even if its bytes are unchanged; reproducible checkouts must preserve that date.
- Publication writes only `assurance/plutus.json`, `assurance/assurance.json` and `assurance/checking-<id>.json`, then removes obsolete checking JSON files while retaining unrelated files and directories. Files are replaced via same-directory temporary files, not truncated through existing symlinks/hard links; a symlinked assurance directory and an environment manifest overlapping generated paths are rejected. Replacement is per-file, not an atomic transaction for the whole bundle. The root `plutus.json` is never an output of this command.
- Added eight real CLI integration tests for emission, raw environment-byte binding, deterministic reruns, stale cleanup, fresh/existing-output dry runs including failures, required/conflicting flags, common options, ordinary-build stability, missing/cached dependencies and symlink protection. Seven focused read-only compilation/dependency tests cover missing/stale/transitive inputs and unchanged filesystem bytes/modification times; a date boundary test covers leap centuries and the four-digit schema range. No existing tests or snapshots were changed.
- Runtime smoke generated the four expected files from the two-property validator fixture, independently recomputed every artifact SHA-256, resolved an environment path containing spaces, observed byte-identical reruns, and checked both dry-run modes against recursive content/mtime snapshots. The fragment id maps `/`→`.` and `.`→`-`; Aiken module names use only `[a-z0-9_./]`, so the map is injective and schema-legal, and ids of plain-identifier paths are unchanged. The Lean namespace is unchanged (`«…»` escaping per segment). Helper references are namespace `.` declared name. Hand-written references keep their meaning: qualified references use the same namespace spelling as before, and declared names still resolve.
- Mechanism, chosen against pinned PlutusCoreBlaster `1c23de8`: fragments accept only `def`/`abbrev` with a closed term profile, without `namespace`, `open`, `@` or named arguments. Alternatives rejected: `abbrev x := ns.x` aliases fail for implicit parameters (observed in Lean 4.24: "don't know how to synthesize implicit argument"); requiring qualified names everywhere would break existing local examples; wrapping in `namespace … end` is outside the command profile.
- Lean elaborates a dotted declaration with its prefixes open, and the innermost match wins. So sibling references in a copy resolve to qualified siblings, checked in plain Lean 4.24. The same rule can rebind a name: inside `x.g`, `f` means `x.f` if that exists. The producer now models this for emitted names. Consumer and Lean library names are outside the model. Retained the original rejection of duplicate leaf names across a closure; independent namespaces for duplicate leaves are not offered.
- Missing-fragment diagnostics now require a lexical name that spells a project helper's qualified declaration exactly (or projects from it), with a related label at that definition. A bare namespace prefix is no evidence of a module reference. Unqualified, unknown and misspelled names are left to consumer elaboration. Residual: a bound variable spelled like a module path and projecting a field with exactly a helper's name is still reported; importing the module or renaming the binder resolves it.
- Policy: imported helpers are written with the full module path. Aiken `use … as` aliases are not Lean names, and no alias is inferred from incidental text.
